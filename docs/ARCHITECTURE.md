# Zenject как способ связывания модулей

В проекте используется Zenject как архитектурный слой композиции, который отвечает за связывание игровых систем, сервисов и runtime-объектов через контейнер зависимостей, а не через жёсткие ссылки между `MonoBehaviour`, синглтоны и ручную инициализацию в сценах.

Такой подход нужен, чтобы отделить бизнес-логику игры от механики её сборки.  
Когда зависимости регистрируются централизованно и внедряются явно, код становится менее связанным, отдельные подсистемы проще заменять, тестировать и развивать независимо друг от друга.

Zenject также даёт проекту управляемый жизненный цикл объектов: сервисы, фабрики, презентеры и другие части игры создаются по заранее описанным правилам, а не хаотично из разных точек кода.  
Это особенно важно для независимых модулей в проекте - например, gameplay, UI, save/load, audio, analytics или state machine - которые должны быть изолированы по ответственности, но согласованно работать в одном runtime-контексте.

Используется в проекте как инфраструктурный инструмент, который помогает реализовать выбранную архитектуру последовательно: сделать зависимости явными, сократить связанность и сохранить предсказуемую структуру по мере роста проекта.

# Разделение приложения на контексты

### Определение контекстов

Основная идея, позволяющая работать со слабо связанными модулями, - разделение приложения на контексты. Контекст представляет из себя DiContainer (В случае этого проекта реализован Zenject), ссылающийся на другой контейнер выше в иерархии контекстов. Каждый контекст содержит точку входа, которая гарантированно при запуске контекста устанавливает нужные зависимости, чтобы их могли использовать модули внутри во время работы контекста. Иерархия контекстов:
### Project Context

Project Context доступен на всем протяжении работы приложения. Его зависимости устанавливаются один раз при запуске и доступны на всем жизненном цикле приложения.
Так Zenject гарантирует, что все сервисы, имеющие неразрешенные зависимости в Project Context, могут получить их в любой момент. Следующие контексты создаются "внутри" Project Context.
## Scene Context

В отличии от Project Context, Scene Context не существует на протяжении всей работы приложения в единственном экземпляре. При каждом переключении сцены старый контекст сцены удаляется (объекты внутри контекста могут получать уведомления о завершении жизненного цикла своего контекста) и запускается контекст новой сцены. В этом контексте принято устанавливать зависимости специфические для конкретной сцены.

### Object Context

Контекст объекта на сцене. Создается "внутри" контекста сцены. Нужен для дополнительной инкапсуляции механик в отдельную "сущность", со всеми ее реализуемыми контрактами и зависимостями внутри контейнера. У любого Object Context есть возможность создать дочерний контекст такого же типа Object Context.

# Точка входа

```cs
public class Program
{
    [RuntimeInitializeOnLoadMethod(RuntimeInitializeLoadType.AfterSceneLoad)]
    public static void Main()
    {
        UnityApplicationBuilder builder = new UnityApplicationBuilder();
		... (Здесть настройка config и Project Context dependncies)
        UnityApplication app = builder.Build();
        app.Run();
    }
}
```

Unity по умолчанию не предоставляет единой точки входа в проект из кода. В проекте применено свое решение с добавлением типов UnityApplicationBuilder и UnityApplication. Эти два класса делают возможным единый вход в проект из одного места в коде. `UnityApplicationBuilder` предоставляет удобную работу с поставщиком конфигурации и с настройкой будущих зависимостей в Project Context. Основная логика приложения запускается на `app.Run();`
### Конфигурация до запуска основной логики
При создании `UnityApplicationBuilder` в него загружается unity asset в ресурсах проекта `ConfigurationBuilder`. Этот asset уже хранит в себе все заранее установленные в редакторе unity нужные для запуска объекты конфигурации. В `Program.Main()` можно добавить свои объекты конфигурации, или прочитать те, которые были добавлены в `ConfigurationBuilder` до этого:
### Получение объекта конфигурации через builder

```cs
if (builder.Configurations.TryGet(out InputSystem_Actions config) == false)
	throw new System.Exception($"Could not find configuration of type {nameof(InputSystem_Actions)}");
    
    (Далее можно использовать полученный экземпляр config)
```

### Добавление объекта конфигурации через builder

```cs
InputSystem_Actions inputActions = new InputSystem_Actions();
builder.AddConfiguration(inputActions);
```

### Установка зависимостей в Project Context через builder

```cs
builder.AddInstaller((container) =>
{
    container
        .Bind<InputSystem_Actions>()
        .ToSelf()
        .AsSingle()
        .OnInstantiated<InputSystem_Actions>((_, isa) => isa.Enable());
});
```

# Модуль сохранения данных, привязанный к системе контекстов

## Центральная система управления сохранениями

В библиотеке за логику переключения между контекстами сохранения отвечает реализация IDataExplorer

Реализация этого интерфейса по умолчанию регистрируется в контейнер ProjectContext из установщика SaveToolProjectInstaller и вы всегда можете получть зависимость IDataExplorer из контейнера:

```cs
[Inject]
public void Construct(IDataExplorer dataExplorer)
{
    _dataExplorer = dataExplorer;
}
```

С помощью IDataExplorer можно обратиться к трем разным контекстам:

```cs
IGlobalDataContext globalContext = _dataExplorer.GlobalDataSet; // Глобальный контекст (1)
ISaveCellContext saveCellContext = _dataExplorer.SaveCellDataSet; // Контекст ячейки сохранения (2)
ISceneDataContext sceneDataContext = _dataExplorer.SceneDataSet; // Контекст сцены (3)

// Метод GetData для всех контекстов:
G globalData = globalContext.GetData<G>();
T saveCellData = saveCellContext.GetData<T>();
S sceneData = sceneDataContext.GetData<S>();

// Метод Save для всех контекстов:
globalContext.Save<G>(globalData);
saveCellContext.Save<T>(saveCellData);
sceneDataContext.Save<S>(sceneData);
```

## (1) Глобальный контекст сохранения

У приложения этот контекст всегда неизменен. Все данные, сохраненные в этом контексте будут доступны для использования, в любой ячейке cохранения и в любой сцене. Также с помощью глобального контекста вы можете открыть ячейку сохранения:

```cs
globalContext.OpenSaveCell();
// Или
globalContext.OpenSaveCell(0);
```

Вызов метода OpenSaveCell без параметра откроет последнюю использованную ячейку, либо вы можете явно указать, какую ячейку хотите открыть. Если ячейки с индексом, который вы указали, не существует, то папка сохранения с таким индексом будет создана автоматически. Метод OpenSaveCell читает всю информацию (кроме папок со сценами) в папке с индексом ячейки, десериализует в объекты и кеширует. Благодаря этому получение данных (GetData()) из ячейки после вызова OpenSaveCell происходит моментально.

## (2) Контекст ячейки сохранения

Контекст остается неизменным, когда игра переключается между разными сценами, но вы можете изменить контекст вручную, способом, указанным выше.

Для загрузки информации сцены можно использовать метод у ISaveCellContext:

```cs
saveCellContext.OpenScene("SampleScene"); // Где "SampleScene" это название сцены 
```

Либо если ISaveCellContext мог быть еще не открыт, можно использовать метод у IDataExplorer (рекомендуется):

```cs
_dataExplorer.OpenSceneDataSet("SampleScene");
```

Этот метод сначала проверит открыт ли ISaveCellContext и только потом вызовет у него OpenScene

## (3) Контекст сцены сохранения

Этот контекст самый низкий по уровню и не может хранить в себе другие контексты. Также он будет заменен на новый созданный ISceneDataContext при переключении сцены (если на новой сцене есть SaveToolSceneInstaller) В отличие от свойств GlobalDataSet и SaveCellDataSet у IDataExplorer, свойство SceneDataSet может вернуть null, если в приложении еще не было открыто ни одной сцены с SaveToolSceneInstaller или если еще ни разу не вызывался метод (ISceneDataContext.OpenScene или IDataExplorer.OpenSceneDataSet)

## Как хранятся данные?

После сохранений структура файлов по пути Application.persistentDataPath будет выглядеть так:

```
=> Папка с названием проекта
    => UnitySaveTool
        => SavedContext.json
        => 0
            => Папка с названием сцены
                => TestSaveData.json
```

Папка "0" это папка которая будет хранить в себе данные игрового прогресса. 0 - это как бы индекс ячейки сохранения, а таких ячеек можно создать сколько угодно и настроить между ними удобное переключение. SavedContext.json как раз запоминает какая ячейка выбрана и библиотека работает с ней по умолчанию. В папке UnitySaveTool помимо SavedContext.json и папок с ячейками сохранения будут также храниться данные, которые были сохранены в глобальном контексте. И наконец папки с названием сцен будут хранить в себе соответственно данные с этих сцен.

Преимущество библиотеки - поддержка четкой структуры в которой сохраняются файлы, и набор инструментов для удобного взаимодействия с ней
